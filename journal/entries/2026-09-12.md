# ACE moves from idea to runnable experiment

This week Maestro moved from asking which music model to start with to preparing a concrete ACE-Step 1.5 audio-personalization experiment. The goal is still a musician's studio: play a part, direct the arrangement, and revise what the machine makes. ACE is now the first audio model we will test for that workflow, not a claim that the studio or a personalized model is finished.

## What changed

I set up an experiment-scoped Python project with `uv` under `experiments/001_ace_audio_personalization/`. It has a recording manifest, audio validation, a composition-level train/validation split, ACE preprocessing and LoRA training hooks, seeded candidate generation, human and AI preference branches, and a matched-seed listening report. The order is deliberate: supervised fine-tuning first, then an experimental offline preference update if human listening gives us a useful signal. This is not yet an RLHF result.

The immediate data plan also sharpened. The model consumes audio, not MIDI, so I can start by recording original piano performances directly; MIDI can be saved alongside them for analysis and editing. Violin and piano–violin duets can enter the same pipeline later. Each take needs a short caption describing what is audible, its instrument, and its provenance. The pilot target is distinct 60–120 second musical ideas rather than many cuts of one composition.

## Current thinking

David Foster remains a musical reference point: expressive piano, broad melodic arcs, rich voicings, orchestral entrances, and harmonic lifts. I want to find out which of those qualities ACE can learn from audio and which require explicit musician control in the studio. A model that produces a plausible surface but cannot preserve my phrase or accept a local correction would not meet the product goal.

Next week's comparison should distinguish *inspiration and evaluation* from *training data*. I can record and train on my own original piano music. If I use Foster compositions or commercial recordings as training material, I first need a clear right to do so; otherwise they remain listening references, and the training set stays with material I own or have permission to use.

## Findings and evidence

- The synthetic end-to-end smoke passed on a local CPU. It prepared two 48 kHz audio examples with distinct composition IDs, made one train/validation split, ran one PyTorch SFT optimizer step, generated four feedback candidates, formed two human and two automated preference pairs, ran one optimizer step for each preference branch, and produced two matched evaluation cases with four variants each. The five automated tests and lint checks passed.
- The smoke uses a tiny stand-in decoder, synthetic audio and tensors, and an audio-energy scorer in place of CLAP. It verifies the orchestration, artifact files, loss/backpropagation, and optimizer paths. It does **not** verify ACE checkpoint loading, ACE preprocessing or generation, adapter compatibility, musical quality, or GPU performance.
- The training code targets the pinned ACE-Step 1.5 checkout and a base-model LoRA on the RTX PRO 5000/C3 environment. No ACE weights have been run on that GPU yet. The first GPU smoke remains a milestone, not a completed result.

## Artifacts completed

The [ACE audio-personalization experiment](../../experiments/001_ace_audio_personalization/README.md) documents the recording format, commands, branch structure, and verification boundary. The synthetic run saved its prepared manifest, checkpoints and metrics, preference pairs, generated clips, and blind-listening index under the experiment's ignored `artifacts/smoke/` directory. The studio prototype remains a separate interface experiment; it is not yet connected to ACE.

## Open questions

- Will the pinned ACE model and preprocessing path run end to end with its real weights on the RTX PRO 5000, and what memory or throughput limits appear?
- How many distinct original piano pieces are needed before the adapter changes the music in a useful way rather than memorizing takes?
- Can captions specify phrasing, voicing, instrumentation, and section-level motion well enough to steer results?
- Which qualities associated with Foster are audible in piano-only material, and which require strings, production, or longer arrangements?
- Do human preferences improve results beyond SFT? The automated scorer only measures a weak prompt/audio proxy, not musical taste.

## Next experiment

Run a minimal **real-ACE GPU smoke** with the pinned checkout and checkpoint bundle on the RTX PRO 5000 or C3, using synthetic or rights-cleared test audio. Then record the first original piano takes, keep any MIDI capture as a companion file, write audible captions and provenance, and start a held-out SFT pilot. Use Foster's music as a reference for the questions and evaluation; add it to training only where the rights are clear. Compare the unmodified ACE model and the first adapter on the same prompts and seeds before deciding whether a preference-training branch is warranted.
